# 约时间助手小程序：竞品分析与工程文档

更新日期：2026-03-09
定位：微信小程序 / Taro + React + TypeScript

---

## 1. 项目目标

做一个以“多人约时间”为核心的微信小程序，帮助发起人快速收集多人空闲时间，并自动得出最合适的候选时间段。

核心要解决的问题：

- 多人会议/聚会/活动很难在微信群里来回确认时间
- 纯文字沟通效率低，容易漏人、漏时间段
- 发起人很难快速看出“哪个时间最多人有空”
- 当参与人数变多时，人工统计的成本急剧上升

一句话定义：

> 一个面向中文用户场景的 When2meet 式微信小程序，用结构化时间收集和可视化决策面板提升多人约时间效率。

## 2. 竞品分析

### 2.1 从你提供的竞品资料中可识别的能力

从首页、创建事件、时间勾选、决策面板等截图和说明来看，竞品已经覆盖了以下能力：

1. **首页聚合入口**
   - 创建时间询问
   - 活动邀请
   - 预约日历
   - 常见问题和案例引导
   - 列表展示历史/当前事件

2. **创建事件的多步流程**
   - 第一步先选择“时间粒度”
   - 支持两种模式：
     - 精确到具体时段（例如 30 分钟粒度）
     - 只选择日期（不关心具体时段）

3. **参与者时间填写**
   - 通过网格化的日期/时段界面选择自己的空闲时间
   - 支持编辑自己的时间
   - 支持可选/已选/不可选状态区分

4. **身份与成员管理**
   - 显示“您的身份”
   - 查看成员列表
   - 存在“代填成员”能力

5. **组织者决策面板**
   - 自动统计参与人数
   - 自动汇总合适时间段
   - 按命中率/人数对时间段排序
   - 支持列表视图 / 时间段视图
   - 可查看某个候选时间段的详情

6. **事件生命周期状态**
   - 例如“搜集中”之类的状态标签
   - 说明事件不是静态的，而是有收集中、待确认、已结束等过程

### 2.2 竞品优点

#### 优点 1：核心路径清晰
竞品最强的一点是，把复杂的“多人协调”拆成了三段：

- 发起人创建
- 参与者勾选
- 系统自动排序

这是非常自然且高频的协作路径，学习成本低。

#### 优点 2：视觉化时间选择很直观
网格化时间表非常适合“看空闲”而不是“写文字”。
用户不需要解释，只需要点选。

#### 优点 3：对组织者友好
组织者最痛的不是“发起”，而是“统计”。
竞品把“决策面板”做成单独入口，这是产品价值最集中的地方。

#### 优点 4：兼容不同约时间场景
通过“精确到时段”和“只选日期”两种模式，竞品覆盖了：

- 会议
- 聚餐
- 培训
- 团建
- 多日活动
- 行程协调

#### 优点 5：有一定传播性
通过“转发给参与者”这种传播方式，小程序天然适合在微信群中扩散。

### 2.3 竞品不足与可优化方向

#### 不足 1：首页信息有点杂
竞品首页同时放了：时间询问、活动邀请、预约日历、案例、FAQ、列表。
新用户第一次进入时，可能不太容易马上分清主任务。

**你的产品可以优化为：**
- 首页只突出一个主按钮：`发起约时间`
- 其他能力放二级入口或后续版本

#### 不足 2：功能边界略宽
竞品似乎同时在做：
- 时间收集
- 活动邀请
- 预约日历

这会让产品目标变宽。

**你的第一版建议更聚焦：**
只做“多人约时间”，先把这个做透。

#### 不足 3：视觉上偏工具化
竞品界面偏功能堆叠，虽然实用，但品牌感和轻量感一般。

**你的机会：**
- 更轻一点
- 更干净一点
- 更像一款“效率工具 + 社交协作”的产品

#### 不足 4：决策结果仍偏“列表展示”
如果只是列出时间段，对用户来说还是要自己再判断。

**你的产品可以加强：**
- 直接推荐 Top 3 最优时间段
- 给出推荐理由：最多人有空 / 连续时段最佳 / 晚上优先等
- 支持一键确认最终时间

#### 不足 5：缺少清晰的闭环动作
从截图看，更多是在“收集”和“分析”，但最终拍板流程不够突出。

**你的产品可以补强：**
- 发起人一键确认最终时间
- 确认后自动生成“已定时间”状态
- 给参与者推送最终结果

### 2.4 你的差异化建议

建议你的产品在第一阶段就做出下面几个差异化：

1. **更聚焦**：只做“约时间”，不同时做太多预约/邀请泛能力
2. **更轻**：首页不复杂，首屏直接创建
3. **更智能**：不只展示数据，还直接推荐候选结果
4. **更闭环**：从发起 → 填写 → 决策 → 确认 完整走通
5. **更适合微信传播**：分享文案、卡片标题、参与流程做得更短更直接

## 3. 产品定位与目标用户

### 3.1 产品定位

一个帮助微信群体快速约时间的轻量协作工具。

### 3.2 目标用户

#### 用户类型 A：组织者
例如：
- HR 组织面试/培训
- 团队负责人约会议
- 班长组织聚会
- 朋友局发起人
- 社群活动组织者

#### 用户类型 B：参与者
例如：
- 被邀请来填时间的人
- 不想来回聊天确认的人
- 希望快速勾选自己空闲时间的人

### 3.3 核心场景

- 5 人以上会议约时间
- 多人聚餐/团建协调
- 社群活动时间收集
- 培训/面试排时间
- 家庭/朋友聚会投票

## 4. 产品功能设计

建议把功能分成 MVP（第一版必做）、V1.1（增强版）、V2（扩展版）。

### 4.1 MVP 功能（第一版必须有）

#### A. 事件创建
发起人可创建一个约时间事件，包括：

- 事件标题
- 事件说明（可选）
- 开始日期
- 结束日期
- 时间模式：
  - 仅日期
  - 精确到时间段
- 时间粒度：
  - 30 分钟
  - 1 小时
- 可选时间范围：
  - 如 09:00 - 22:00
- 是否限制参与人数（可选）
- 发起人昵称

#### B. 分享/邀请参与者
- 生成微信分享卡片
- 支持转发到好友/群聊
- 参与者点击即可进入事件

#### C. 参与者填写空闲时间
- 输入昵称
- 查看事件信息
- 在网格中勾选有空时间
- 提交自己的空闲时间
- 后续可再次编辑

#### D. 统计与决策
- 统计总参与人数
- 计算每个时间段有空人数
- 生成候选时间段排序
- 展示 Top N 推荐时间
- 支持查看某个时间段的参与明细

#### E. 发起人确认最终时间
- 从候选结果中选择最终时间
- 将事件状态改为“已确定”
- 参与者进入后能看到最终结果

#### F. 我的事件
- 我发起的事件
- 我参与的事件
- 可查看事件状态

### 4.2 V1.1 增强功能

- 代他人填写时间
- 备注“暂定/尽量/不能参加原因”
- 按条件筛选候选时间（工作日/晚上/周末）
- 候选时间自动聚合连续时段
- 分享海报/更好的分享文案
- 到期自动停止收集
- 事件提醒

### 4.3 V2 扩展功能

- 活动邀请（确定时间后统计参加/不参加）
- 预约日历 / 个人可预约空闲表
- 微信登录与用户体系
- 通知订阅消息
- 数据导出
- 企业/团队版（组织空间）

## 5. 用户角色与权限

### 5.1 发起人
权限：
- 创建事件
- 编辑事件基础信息
- 查看所有参与结果
- 查看决策面板
- 确认最终时间
- 结束/关闭事件

### 5.2 参与者
权限：
- 查看事件说明
- 填写自己的空闲时间
- 编辑自己的时间
- 查看最终确认时间

### 5.3 游客模式
为了降低门槛，MVP 建议先支持游客参与：
- 不强制登录
- 通过昵称 + 本地标识参与

后续再考虑微信身份绑定。

## 6. 用户交互流程

### 6.1 主流程：发起约时间

1. 首页点击“发起约时间”
2. 填写基本信息
3. 选择时间模式（日期 / 时段）
4. 设置可选日期范围与时间范围
5. 创建成功
6. 转发给参与者

### 6.2 主流程：参与者填写时间

1. 通过分享卡片进入事件
2. 输入昵称
3. 查看事件标题、说明、候选范围
4. 在时间网格中勾选空闲时间
5. 提交
6. 可返回再次编辑

### 6.3 主流程：发起人决策

1. 进入事件详情
2. 查看参与人数和填写进度
3. 打开决策面板
4. 看系统推荐 Top 3 时间段
5. 查看某个时间段谁有空、谁没空
6. 确认最终时间
7. 事件转为已确定

### 6.4 辅助流程：查看我的事件

1. 进入“我的”页面
2. 查看“我发起的”和“我参与的”
3. 点击进入详情页

## 7. 页面结构设计

建议第一版页面控制在 6~8 个核心页面，避免过重。

### 7.1 首页 `/pages/home/index`
目的：快速发起和查看事件列表

模块建议：
- 顶部 Slogan：一句话说明用途
- 主按钮：发起约时间
- 最近事件列表
- 快捷筛选：全部 / 我发起的 / 我参与的

设计建议：
- 首页尽量轻，不要堆太多 FAQ 和二级业务
- 让用户 3 秒内知道下一步要点哪里

### 7.2 创建事件页 `/pages/create/index`
目的：完成事件创建

建议拆成分步式：
- Step 1：选择模式（日期 / 时段）
- Step 2：填写标题、说明
- Step 3：选择日期范围
- Step 4：设置时段规则
- Step 5：确认创建

### 7.3 事件详情页 `/pages/event/detail`
目的：展示单个事件基本信息和用户入口

模块：
- 标题、说明、状态
- 时间范围
- 我的身份/昵称
- 本人时间入口
- 成员列表入口
- 决策面板入口（发起人可见）
- 分享按钮

### 7.4 时间填写页 `/pages/event/availability`
目的：勾选时间

模块：
- 顶部说明
- 日期列 + 时间行网格
- 可选/已选图例
- 清空/提交按钮

设计建议：
- 第一版优先支持点击切换格子
- 后续再加拖动批量选择

### 7.5 决策面板页 `/pages/event/decision`
目的：帮助发起人快速选定时间

模块：
- 参与人数统计
- 推荐 Top 3
- 候选时间段列表
- 命中率 / 有空人数
- 查看详情按钮
- 一键确认按钮

### 7.6 时间段详情页 `/pages/event/slot-detail`
目的：查看某个时间段的参与情况

模块：
- 时间段信息
- 有空名单
- 没空名单
- 备注信息（后续版本）

### 7.7 我的页面 `/pages/me/index`
目的：管理用户自己的事件

模块：
- 我发起的
- 我参与的
- 最近浏览

## 8. 界面风格建议

### 8.1 整体风格
建议关键词：
- 轻量
- 清晰
- 工具感但不冰冷
- 有一点社交产品的友好感

### 8.2 视觉方向
- 主色：绿色 / 蓝绿色 / 清爽橙色点缀
- 大按钮、大留白
- 卡片式信息块
- 时间网格保持高对比、强可读性

### 8.3 关键界面原则

#### 首页
- 一个主操作最醒目
- 列表信息只保留必要字段

#### 时间网格
- 已选状态必须非常明显
- 日期与时间标签不能太挤
- 颜色说明要固定在底部或顶部

#### 决策面板
- 排序结果要一眼看懂
- 推荐理由要明确
- “确认最终时间”按钮一定要强提示

## 9. 数据结构建议（MVP）

以下是逻辑模型，不限定后端实现方式。

### 9.1 Event（事件）
- id
- title
- description
- type: `date` | `timeslot`
- dateStart
- dateEnd
- timeStart
- timeEnd
- slotMinutes
- status: `collecting` | `confirmed` | `closed`
- organizerId
- organizerName
- finalSlotId（可空）
- createdAt
- updatedAt

### 9.2 Participant（参与者）
- id
- eventId
- name
- role: `organizer` | `participant`
- joinedAt

### 9.3 Availability（空闲时间）
- id
- eventId
- participantId
- slotKey
- available: true/false
- updatedAt

### 9.4 TimeSlot（时间段）
- slotKey
- eventId
- date
- startTime
- endTime

### 9.5 FinalDecision（最终决策）
- id
- eventId
- slotKey 或 slotGroup
- confirmedBy
- confirmedAt

## 13. 风险与注意事项

### 风险 1：第一版做太宽
建议不要一上来把“活动邀请”“预约日历”“提醒系统”全做进来。

### 风险 2：时间选择交互做太复杂
第一版不要追求拖拽、框选、复杂批量操作，先把点击勾选做好。

### 风险 3：权限与身份混乱
发起人、参与者、游客的操作权限要从一开始就定义清楚。

### 风险 4：推荐算法过早复杂化
第一版直接按“有空人数最多”排序就够了，后面再加更复杂规则。

---

## 14. 最终建议

如果你希望这个项目尽快落地，我建议：

1. **只做“多人约时间”这个核心能力**
2. **先做 MVP，不分散到预约日历/活动邀请等更宽的功能**
3. **先把发起、填写、统计、确认闭环做通**
4. **页面宁可少，也不要乱**
5. **先用假数据做完整演示，再接真实后端**

最推荐的开发顺序是：

- 第一步：搭 Taro 项目骨架
- 第二步：做页面和假数据
- 第三步：跑通事件与填写流程
- 第四步：做决策面板
- 第五步：接真实数据和分享能力
